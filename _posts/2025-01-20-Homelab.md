As an aspiring cybersecurity professional, hands-on experience is crucial for developing the skills needed for this ever-evolving industry.
I designed this homelab to dive further into network infrastructures and simulate real-world environments and challenges providing a secure playground for experimentation.

In this post, i'll walk you through the architecture of homelab, which includes **pfSense** acting as a **Double NAT Firewall and Router**, Isolated virtualized environment for penetration testing, **Active Directory** labs, and a **Raspberry Pi 5** running **Kali Linux**. 
By taking advantage of **virtualization** and using **pfSense** To isolate subnets I created an efficient and scalable homelab.

## Let's break this down!
At the heart of this setup is my **Home Router** which connects to a **Managed Layer 2 Switch**. This switch allows communication between my **Raspberry Pi 5** and the virtualized components running on the **Host PC** Through **VLANs**.
I opted for this setup because the **Host PC** is currently my daily computer.
Using the switch allows me to create **port-based VLANs,** making it easy to bridge the **Host PC** and **Raspberry Pi 5** when the lab is running and switch back to the home network when it’s off.
I created two **VLAN IDs**, **VLAN ID 1** is the default and provides internet and **VLAN ID 2** is for my homelab and provides isolated communication between my **Raspberry Pi 5** and **Host PC**. 
I use a **USB Wireless Network Adapter** when the lab is running to provide wifi to the **Host PC** and some virtualized components. 

### pfSense

The **Host PC** is running **VirtualBox** to host multiple virtual machines and a **pfSense Firewall/Router**. **pfSense** is attached to four network adapters and plays a crucial role in network segmentation, configured to manage three isolated subnets:
- 10.0.0.1/24 (LAN) **Bridged to the Switch**: network for basic connectivity and management
- 10.6.6.1/24 (Isolated) **Internal Network**: A dedicated network isolated from internet access for intentially vulnerable machines
- 10.80.80.1/24 (Active Directory Lab) **Internal Network**: A simulated enterprise network for configuring and securing Active Directory

I enabled **pfSense ISC DHCP daemon** for the subnets **LAN** and **Isolated**, while disabling it on the **Active Directory** subnet as the domain controller will act as the **DHCP** **Server** for this subnet.

**pfSense** evaluates its firewall rules from top to bottom.
Meaning, the first rule in the list takes precedence over the rules below.
For the **Isolated** interface, I set a rule that blocks access to everything.
However, since I added a rule above it that allows packets to the **Kali** machine.
Any machine connected to that interface will be able to communicate with the **Kali** machine and vice versa.

To test that the firewall is working properly lets start up metasploitable2 and check if we pull an **IP** from the **DHCP** server on **pfSense** and only can communicate with the **Kali** machine.
